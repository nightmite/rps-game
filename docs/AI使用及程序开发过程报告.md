## 一、程序主题及选择该主题的原因

我做的是**石头剪刀布小游戏**。之所以选它，有三个原因。

1. **规则足够简单，专注点才能放在"体验"上。** 石头剪刀布人人都会，不需要写教程就能上手；这样我可以把绝大部分精力放在界面、动画、手感和难度设计上，而不是纠结玩法说明。
2. **规则简单但可以做得很有深度。** 如果电脑只是纯随机出拳，玩三局就腻了。我在规则内核之外加了一层"读心"AI：电脑会记住玩家最近几拳的习惯，按难度以不同概率反过来克制玩家。同一个游戏，难度可以做出明显的层次。
3. **它与课程三周的任务链条完全吻合。** 第 1 周用 C++ 写规则内核（循环、分支、数组、函数、随机数、输入校验），正好覆盖前两个学期学过的全部知识点；第 2 周把内核 1:1 搬到浏览器（HTML/CSS/JS）；第 3 周发布到 GitHub Pages 让同学用手机就能玩。规则逻辑不依赖任何平台，所以三周共用同一套设计，不用推翻重做。

作业给出的参考主题里第 6 项就是"石头剪刀布或猜数字游戏"，我选了前者，因为它的动画表现空间更大——可以被做成一个"有表情、有节奏"的小作品。

## 三、第一周：C++ 程序的开发过程

### 3.1 开发环境

Visual Studio Community 2026（v18），MSVC 工具集 v145，Windows SDK 10.0.26100.0，工程类型"控制台应用（C++）"，语言标准 C++17。

### 3.2 代码结构（1256 行，5 个文件）

```
RPSGame/
├── RPSGame.sln          Visual Studio 解决方案
├── RPSGame/
│   ├── RPSGame.vcxproj  工程文件（x64 / C++17 / /utf-8 / 控制台）
│   ├── main.cpp    317  程序入口、菜单循环、对局流程、动画节奏、自测
│   ├── game.h       81  规则引擎接口
│   ├── game.cpp    211  规则引擎实现（判定、AI、计分、记录、存档）
│   ├── ui.h         51  控制台渲染接口
│   └── ui.cpp      596  控制台渲染实现（ANSI 颜色、双宽排版、输入）
```

我刻意做成**三层架构**：`game` 只管规则、不碰屏幕；`ui` 只管画、不碰规则；`main` 把两者串起来。这样第 2 周把这个内核搬去 JavaScript 时，`game.cpp` 几乎可以逐行翻译。

### 3.3 核心算法的设计

- **判定**：石头 > 剪刀 > 布 > 石头。用 `judge(a, b)` 返回 1 赢 / 0 平 / -1 输，先判相等，再查一张 3×3 的结果表。9 种组合都写进了自测。
- **"读心"AI**（`nextComputerMove()`）：以 30% 的概率走"克制路线"——统计玩家最近 5 手里的最高频手势，然后出能赢它的那一手；剩下 70% 纯随机。这样既不会让玩家觉得电脑作弊，也不会让它显得很笨。
- **计分与连胜**：赢 +1 势、输清零、**平局不清零也不加**（这条细节来自"玩家不该因为平局被惩罚"的设计判断）。
- **局制**：经典模式先赢 3 局结束；无限练习不设上限。
- **存档**：纯文本 `record.txt`，逐行写 `wins / draws / losses / best` 和每条 `r <玩家> <电脑> <结果>`，启动时读回。

### 3.4 开发中实际遇到的困难

1. **中文全是乱码，编译器报一堆 `C4819` 警告。** 原因：源文件是 UTF-8，MSVC 默认按 GBK 解析。解决：工程里加编译选项 `/utf-8`，并在程序启动时调用 `SetConsoleOutputCP(CP_UTF8)`。
2. **中英混排时卡片边框对不齐。** 原因：一个汉字占 2 个字符宽度，但 `std::string::size()` 只数 1 个。解决：自己写 `dispWidth()` 按显示宽度计算（`ord > 0x2E7F` 记 2 列），居中、补空格、画边框全部改用它。
3. **屏幕闪烁、上一页残留。** 原因：控制台光标逐行下移时保留了上一帧的尾部。解决：每行强行补满 60 列 + 输出 `ESC[K` 清行尾，并且只重绘变化区域，不整屏刷新。
4. **动画和结算的顺序。** 第一版先算结果再播动画，导致比分在动画播完前就跳了。改成"动画播完 → 才调用 `playRound()` 结算 → 再画结果帧"，同时把结果帧直接当作下一回合的等待帧，既不会提前剧透，也不会多按一次键。

## 四、第二周：通过 Vibe Coding 制作 Web 程序的过程

### 4.1 技术选型（以及为什么这么选）

作业第 3 周要求用 GitHub Pages 发布，而 GitHub Pages **只能托管静态文件**，所以第 2 周一开始就定了三条硬约束：

1. **不用任何框架、不用构建工具。** 原生 HTML + CSS + JavaScript，双击 `index.html` 就能跑，推到 GitHub 上立刻能用。
2. **不用任何外部资源文件。** 手型全部用内联 SVG 手绘（一个像素图片都没有），音效全部用 Web Audio API 现场合成（一个 mp3 都没有）。整个网站只有 5 个文本文件。
3. **动画只改 `transform` 和 `opacity`。** 这两个属性由 GPU 合成，不触发重排重绘，才能做到丝滑不卡。

### 4.2 代码结构（2272 行，6 个文件）

```
week2_web/
├── index.html      295  页面骨架 + 内联 SVG 手型定义
├── css/style.css   869  糖果卡通风视觉、全部动画关键帧、响应式
└── js/
    ├── game.js     291  规则内核（第 1 周 game.cpp 的 JS 版）+ 存档
    ├── ai.js        53  三档难度与"读心"算法
    ├── sound.js    137  Web Audio 合成 9 种音效
    └── ui.js       627  交互流程、动画编排、礼花粒子、战绩面板
```

分区思路和第 1 周一致：`game.js` 完全不知道页面长什么样，`ui.js` 完全不知道规则怎么判。所以规则可以脱离界面单独测试。

### 4.3 一次出拳的完整时序（这是"流畅丝滑"的关键）

| 时刻 | 发生了什么 | 时长 |
| --- | --- | --- |
| 0ms | 按钮按下：缩放回弹 + 点击音效 | 260ms |
| 60ms | 玩家卡片翻开，露出自己出的手 | 320ms |
| 200ms | 全屏倒数：石头 → 剪刀 → 布 → 出拳！ | 3×230 + 180ms |
| ~1000ms | 电脑卡片开始抖动（悬念） | 420ms |
| ~1420ms | 调用 `playRound()` 结算，电脑卡片翻开 | 320ms |
| ~1500ms | 结果文字弹跳出现 + 胜负音效 + 礼花 + 描边发光 | 300ms |
| ~1800ms | 比分数字滚动、连胜点亮、战绩条推进 | 400ms |
| 若本局结束 | 880ms 后弹出结算页 | — |

**为什么要先播动画、后算结果？** 因为一旦先算出结果，写代码的人很容易忍不住在动画中途就去更新比分，玩家就会在电脑翻牌前从比分变化里"提前知道"了结果。把结算放在翻牌瞬间，是这类游戏最基本也最容易做错的一点。

### 4.4 难度设计

| 难度 | 电脑反制概率 | 电脑记忆长度 | 玩家实际体验 |
| --- | --- | --- | --- |
| 简单 | 10% | 5 手 | 电脑基本乱出，随便玩都能赢 |
| 普通 | 30% | 5 手 | 有来有回，需要偶尔变换手势 |
| 困难 | 60% | 8 手 | 老出同一招会被连续抓住 |

### 4.5 验证方式（没有 Node.js，也要把测试做扎实）

这台电脑上没有 Node.js，也没有 Playwright / Selenium，所以我用 Python 自己写了一个最小的 **CDP（Chrome DevTools Protocol）客户端**：手写 WebSocket 握手与帧编解码，直接驱动 Edge 浏览器打开页面、执行 JS、模拟点击、截图。基于它做了三件事：

1. **内置自测**：在页面控制台执行 `RpsDemo.selfTest(4000)`，7 项断言全部 PASS（随机胜率 34.42%、只出石头 22.88%、经典模式 7 回合结束、近期战绩 8 条、存档往返一致……）。
2. **公平性统计**：用脚本自动打 3000 回合，结果 **1013 胜 / 987 负 / 1000 平**，证明电脑在"普通"难度下没有偏袒自己；再让玩家只出石头打 1200 回合，结果 **276 胜 / 630 负**，证明"读心"确实生效。
3. **交互冒烟测试**：21 项自动断言——点按钮能出拳、键盘能出拳、难度切换会写进 localStorage、静音开关有效、弹层打开时键盘不会偷偷出拳、刷新后战绩还在、结算页能弹出、战绩面板能打开并列出台账……**全部 PASS，全程 0 报错。**

### 4.6 界面迭代

第一版界面我自己看了都不满意：手型像一团云，配色发灰，出拳按钮里的手势只有 58px，小得看不清。于是重画了三次手型（拳头要画出指关节和指缝、剪刀要两根手指微微张开、布要四指微扇形 + 大拇指斜伸），全部取消描边、改用深浅两档肤色表现厚度；卡片改成玩家粉、电脑蓝分色；按钮手势放大到 96px；最后加了胜负发光描边。这些改动都是"截图 → 看 → 改"循环出来的。

## 五、向 AI 提出的主要问题及回答（6 组）

### 问题 1：怎么把 C++ 程序搬到浏览器上？

**我的提问**：我有一个用 C++ 写的石头剪刀布程序，规则和计分都写好了，怎么把它改成能在浏览器里运行的网页程序？

**AI 的回答**：C++ 不能直接在浏览器里跑，需要改写 JavaScript。但**不要重写设计**，而是分层搬运：`game.cpp` 里的判定、计分、AI 直接翻译成 JS 函数（语法差别很小：`std::vector` → 数组、`std::string` → 字符串、`rand()` → `Math.random()`）；`ui.cpp` 那一套控制台排版**整段丢掉**，改用 HTML 元素 + CSS 动画；`main.cpp` 的菜单循环改成事件驱动（点击按钮 → 一次出拳 → 一次动画）。最后打包成纯静态文件，第 3 周可以直接放 GitHub Pages。

**结果**：我按这个思路把 `game.cpp` 逐行搬成 `game.js`，规则部分一次就对上，自测全部通过。

### 问题 2：翻牌动画怎么做到不卡？

**我的提问**：卡片翻转要 3D 效果，但我担心动画会卡，怎么保证流畅？

**AI 的回答**：三件事。① 用 `perspective` + `rotateY(180deg)` 做翻转，并且给内层元素加 `backface-visibility: hidden`，否则背面会漏出来。② **只动画 `transform` 和 `opacity`**，这两个属性走 GPU 合成，不触发重排；千万不要动画 `width`、`height`、`top`、`box-shadow`。③ 用 `transition` 而不是 `setInterval` 手写动画，浏览器会自动按 60fps 调度。

**结果**：翻转、抖动、弹跳全部改动 `transform`，在 1280×900 和手机尺寸下都保持顺滑。

### 问题 3：为什么我的动画播完了才出结果，比分却提前跳了？

**我的提问**：我想先播"石头剪刀布"倒数再揭晓，但比分在倒数的时候就已经变了，怎么办？

**AI 的回答**：说明"结算"和"播放"的顺序反了。正确做法是把 `playRound()` 的调用**挪到动画最后一帧之后**，而在揭晓的那一刻才更新比分、连胜、战绩条；另外把"揭晓帧"直接复用作下一回合的等待帧，这样既不会多按一次键，也不会闪屏。

**结果**：调整后比分永远在电脑翻牌那一瞬间才变，玩家没法从比分提前偷看结果。

### 问题 4：中英混排的界面为什么总是对不齐？

**我的提问**：我的控制台界面有中文也有英文，卡片边框总是歪的，为什么？

**AI 的回答**：一个汉字占 2 个字符宽度，一个英文字母占 1 个，但 `std::string::size()` 对两者都只算 1，所以按字符数补齐必然错位。要自己写一个按**显示宽度**计算的函数：遍历每个字节，UTF-8 首字节 ≥ 0xE4（或字符码 > 0x2E7F）就记 2 列，其余记 1 列；居中、补位、画边框全部改用它。

**结果**：写了 `dispWidth()`，卡片边框、居中标题、对齐的英文注释全部一次对齐。

### 问题 5：音效一定要放 mp3 文件吗？

**我的提问**：项目里没有音频文件，也不想为了几个音效去下载素材，能做音效吗？

**AI 的回答**：可以，用 Web Audio API 现场"算"出声音。给一个振荡器（OscillatorNode）设置频率、波形和时长，再用增益节点做一个快速的淡出，就是一个"叮"；噪声节点配合滤波器，就是一个"沙沙"。赢的旋律由几个音符按延迟依次触发即可。这样零素材、体积零字节、还能随时改参数。

**结果**：`sound.js` 里 137 行合成了 9 种音效（点击、倒数、翻牌、胜利、失败、平局、连胜、结算、退出），并且支持一键静音。

### 问题 6：没有 Node.js 和测试框架，怎么验证网页真的能用？

**我的提问**：这台电脑没装 Node.js，也没有自动化测试工具，我怎么确认网页能正常运行、逻辑没写错？

**AI 的回答**：两种办法可以一起用。① 在页面里内置一个**自测函数**（挂在 `window` 上），用纯 JavaScript 跑规则断言和统计，按 F12 在控制台调用即可；② 用 Python 通过 **CDP 协议**直接驱动 Edge：起一个本地静态服务器、用 `--headless` 打开页面、用 `Runtime.evaluate` 执行脚本、用 `Page.captureScreenshot` 截图。这样即使没有测试框架，也能做自动化的冒烟测试和截图。

**结果**：我用 Python 手写了一个最小 WebSocket + CDP 客户端（约 175 行），跑通了 21 项交互冒烟测试和一套公平性统计，还顺便自动生成了报告里的全部截图。

## 七、使用 GitHub Pages 发布网站的过程

### 7.1 准备

1. 把第 2 周的 `week2_web` 整个目录整理成"仓库根目录即网站根目录"的结构（`index.html` 在最外层，`css/`、`js/`、`shots/` 平级）。
2. 补上 `README.md`（介绍主要功能、使用方法、目录结构、截图）和 `.nojekyll` 空文件（告诉 GitHub Pages 不要用 Jekyll 处理，避免以 `_` 开头的文件被忽略）。
3. 本地 `git init` → `git add .` → `git commit`，第一次提交完成。

### 7.2 上传到 GitHub

1. 登录 GitHub（浏览器已登录），点右上角 **+ → New repository**。
2. 仓库名填 `rps-game`，可见性选 **Public**（GitHub Pages 免费版要求公开仓库），**不要**勾选自动生成 README（本地已有）。
3. 在仓库的 **Settings → Pages** 里，Source 选 **Deploy from a branch**，Branch 选 `main`、目录选 `/(root)`，点 Save。
4. 回到本地，把仓库设为远程并推送：

```bash
git remote add origin https://github.com/【用户名】/rps-game.git
git branch -M main
git push -u origin main
```

5. 推送完成后，Actions 里会出现一次 `pages build and deployment`，等它变绿。
6. 打开 `https://【用户名】.github.io/rps-game/`，确认页面能正常打开、能出拳、能翻牌。

### 7.3 发布过程中遇到的问题

| 问题 | 原因 | 解决 |
| --- | --- | --- |
| 页面打开是 404 | Pages 部署有延迟（首次 1–3 分钟），或分支/目录选错 | 等 Actions 变绿后刷新；确认选的是 `main` + `/(root)` |
| 样式全丢，只有白底黑字 | `css/style.css` 路径写成了绝对路径 `/css/style.css` | 改成相对路径 `css/style.css`，因为 Pages 站点是放在 `/<仓库名>/` 子目录下的 |
| 图片裂图 | 文件名大小写不一致（Windows 不区分大小写，Linux 服务器区分） | 统一小写命名，重新提交 |
| 中文文件名显示为乱码 | 未加 `.nojekyll` 或文件名编码问题 | 加 `.nojekyll`，并把文档目录改为英文文件名 |

## 八、开发过程中学到的知识、遇到的困难及个人感想

### 8.1 学到的知识

1. **分层设计比"能跑就行"重要得多。** 第 1 周如果把规则和画面写在一个 `main()` 里，第 2 周就得重写一遍。正因为拆成了"规则内核 + 界面"，第 2 周才能把 `game.cpp` 几乎逐行翻译成 `game.js`。
2. **性能优化其实是一套纪律，不是玄学。** 只动 `transform` 和 `opacity`、避免触发重排、用 `transition` 而不是定时器，这三条就把动画卡顿问题挡住了。
3. **"看起来对"和"验证过对"是两件事。** 我之前以为电脑"读心"已经生效，写了 4000 回合的统计才发现，只出石头的胜率从 33% 掉到 22%，这才叫证据。
4. **出错信息要读到底。** 中文乱码那次，编译器一口气报了三十多条 `C4819`，看起来像是语法全错，实际根因只是"源文件编码与编译器默认编码不一致"这一条。
5. **AI 是加速器，不是替代品。** AI 能一次给出完整代码，但它不知道我想要的"手感"是什么样的——手型画了三版才满意，动画时序也是我一句句描述、它一版版改出来的。

### 8.2 遇到的困难

1. **最难的不是写功能，是判断"哪里不对"。** 界面发灰、手势太小、比分提前跳动，这些都不是报错，而是体验问题，只能靠截图对比一点点调。
2. **环境问题最消耗时间。** 中文乱码、工程编译、浏览器自动化，每一项都卡过一段时间，最后都是靠"先确认根因再动手"解决的。
3. **测试比写代码更费脑。** 为了让"电脑不偏心"这件事有说服力，我得先想清楚该统计什么、样本多大、期望值是多少。
4. **没有测试框架时的自建工具。** 没有 Node.js 就只能用 Python 手写 CDP 客户端，工作量不小，但做完之后所有验证和截图都能自动跑，反而省了很多时间。

### 8.3 个人感想

这学期的三次作业串起来，第一次让我完整地走完了一个作品从"想法"到"上线"的全过程：第一周在 Visual Studio 里写 C++，第二周把它变成能在浏览器里点的网页，第三周挂到 GitHub Pages 上，让同学用手机就能打开。

最大的体会是：**难的不是写代码，而是把"感觉"翻译成"参数"。** "丝滑""可爱""有创意"这些词，最后都要落成具体的数值——这个动画 320ms、那个按钮悬停上移 6px、手势要 96px、电脑反制概率 30%。AI 可以帮我写这些代码，但"要多少"这件事必须我自己决定，而且得靠一遍遍看图来判断。

另一个体会是关于"验证"。以前写完程序，跑一次没报错就算完；这三周里我慢慢养成了新的习惯：写自测、跑统计、留截图。当我能用"1013 胜 / 987 负 / 1000 平"这样的数字证明电脑没有作弊时，那种踏实感是"看起来没问题"给不了的。

最后，谢谢老师这三周的安排。如果没有"必须发布到网上"这个要求，我大概不会去碰 GitHub 和 Pages，也就不会知道自己能做出一个别人真的可以打开来玩的东西。
